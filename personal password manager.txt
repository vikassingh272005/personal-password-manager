Yes — and if you're going to build this, I’d make it a **real zero-knowledge password manager**, not just a CRUD app with a `password` column.

The central rule should be:

> **Your server authenticates you, but it should never possess the keys required to decrypt your vault.**

That distinction drives almost the entire architecture.

For the cryptography, use established primitives rather than inventing anything. OWASP recommends Argon2id for password protection, and the current RustCrypto crates provide Argon2 and AES-GCM implementations. ([OWASP Cheat Sheet Series][1]) Passkeys/WebAuthn are also a strong option for authenticating to your service. ([MDN Web Docs][2])

# 2. What the application actually manages

There are two different types of credentials here, and they must **not** be confused.

### A. Your password-manager account

This is:

```text
You
 └── Password Manager Account
      ├── email
      ├── authentication
      ├── passkeys
      ├── devices
      └── encrypted vault
```

### B. Accounts inside your vault

For example:

```text
Vault
├── Google
│   ├── username
│   ├── password
│   └── notes
│
├── GitHub
│   ├── username
│   ├── password
│   └── 2FA information
│
├── Instagram
│   ├── username
│   └── password
│
└── College
    ├── username
    └── password
```

The application manages **your own credentials** and account metadata. It should not attempt to log into or control third-party accounts without their normal APIs/authorization.

# 6. Database schema

Here's a production-oriented starting point.

## users

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY,
    email TEXT NOT NULL UNIQUE,
    password_hash TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Important distinction:

`password_hash` is the hash for logging into **your password-manager service**.

It is **not** the encryption key for the vault.

---

## vaults

```sql
CREATE TABLE vaults (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,

    version INTEGER NOT NULL DEFAULT 1,

    kdf_algorithm TEXT NOT NULL,
    kdf_memory INTEGER NOT NULL,
    kdf_iterations INTEGER NOT NULL,
    kdf_parallelism INTEGER NOT NULL,

    kdf_salt BYTEA NOT NULL,

    encrypted_vault_key BYTEA NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    UNIQUE(user_id)
);
```

# 11. Should vault entries have individual database rows?

There are two approaches.

### Approach A — individual encrypted records

```text
database

item 1 → encrypted
item 2 → encrypted
item 3 → encrypted
```

### Approach B — encrypted vault

```text
database

vault → one encrypted blob
```

For your first production implementation, I'd use **encrypted vault snapshots**, with an optional encrypted item index later.

This makes the zero-knowledge model much easier to reason about.

# 13. Encryption hierarchy

This is one of the most important parts.

Don't do:

```text
Master Password → AES encryption
```

Instead:

```text
                  MASTER PASSWORD
                         │
                         ▼
                     Argon2id
                         │
                         ▼
                 Password-Derived Key
                         │
                         ▼
                      HKDF
                         │
                         ▼
                Key Encryption Key
                    (KEK)
                         │
                         ▼
             Encrypt Vault Key
                         │
                         ▼
                Vault Encryption Key
                    (VEK)
                         │
                         ▼
                 AES-256-GCM
                         │
                         ▼
                  Vault Ciphertext
```

### Why?

The **VEK** can be random.

For example:

```text
VEK = 256 random bits
```

The master password doesn't directly encrypt millions of bytes of vault data.

Instead, the password-derived key protects the VEK.

This makes future password changes much easier.

---

# 14. Master-password change

Suppose:

```text
Old password
     ↓
Old KEK
     ↓
Decrypt VEK
```

Then:

```text
New password
     ↓
New Argon2id
     ↓
New KEK
     ↓
Encrypt same VEK
```

You don't need to decrypt/re-encrypt the entire vault.

That's a **huge architectural advantage**.

---

# 15. Encryption envelope

Store something like:

```json
{
  "version": 1,
  "algorithm": "AES-256-GCM",
  "kdf": "Argon2id",
  "kdf_salt": "...",
  "nonce": "...",
  "ciphertext": "...",
  "tag": "..."
}
```

In implementation, you can serialize this as a compact binary format rather than JSON.

AES-GCM should use unique nonces; the RustCrypto documentation specifically notes nonce uniqueness requirements. ([Docs.rs][4])

# 16. Password-manager authentication

There are actually **two authentication layers**.

### Layer 1 — server authentication

```text
Email
+
Account authentication
+
Passkey / MFA
```

This determines:

> "Is this user allowed to access their encrypted vault?"

### Layer 2 — vault unlock

```text
Master Password
        ↓
      Argon2id
        ↓
     Vault Key
        ↓
    Decrypt Vault
```

The backend doesn't need the master password.

# 18. Recovery problem

This is where password managers get genuinely difficult.

If the server doesn't know your master password and doesn't have your decryption key, then:

```text
Forgot master password
```

cannot simply mean:

```text
Send reset email
```

because that would allow the server to decrypt the vault.

Instead provide:

### Recovery Key

During setup:

```text
Your Recovery Key

XXXX-XXXX-XXXX-XXXX
XXXX-XXXX-XXXX-XXXX
XXXX-XXXX-XXXX-XXXX

⚠️ Store this somewhere safe.
```

The recovery mechanism should be designed so that possession of the recovery material is sufficient to regain access, while the server still cannot decrypt the vault by itself.

```text
      ↓
```

# 29. Conflict resolution

You eventually need:

```text
Device A
   │
   ├── vault version 14
   │
Device B
   │
   └── vault version 15
```

Use:

```text
vault_version
revision
updated_at
device_id
```

Initially, simplest safe behavior:

```text
conflict detected
       ↓
download both versions
       ↓
client resolves
       ↓
new merged vault
```

Don't silently overwrite one device's changes.

# 30. Threat model

You should explicitly document what you're defending against.

### Protect against

```text
✓ Database leak
✓ Backend administrator reading vault
✓ Stolen session
✓ Network interception
✓ Modified ciphertext
✓ Password guessing
✓ CSRF
✓ XSS
✓ SQL injection
✓ Brute-force login
✓ Device revocation abuse
```

### Harder problems

```text
⚠ Malware on unlocked device
⚠ Browser extensions
⚠ Keyloggers
⚠ Compromised operating system
⚠ Physical memory attacks
```

No web application can magically make a compromised device trustworthy.

Your backend should never receive:

```text

❌ Vault encryption key
❌ Plaintext stored password

❌ Plaintext recovery secret
```

The backend may receive:

```text

✓ Authentication information
✓ Encrypted vault
✓ Encrypted metadata
✓ Passkey public keys

✓ Security event metadata
```

# 4. CRYPTOGRAPHIC ARCHITECTURE

The VEK must be generated from a cryptographically secure random source.

# 5. KDF

Use Argon2id.

Store the parameters required to reproduce the derivation:

* algorithm
* memory cost
* iteration count
* parallelism
* random salt
* version

Do not hard-code undocumented parameters.

Make the parameters configurable through a security configuration.

Use a safe production baseline and benchmark the chosen settings on the target hardware.

Never replace Argon2id with SHA-256 for password derivation.

Support future KDF parameter upgrades.

# 6. ENCRYPTION

Use authenticated encryption.

Use AES-256-GCM or another explicitly approved AEAD implementation.

Every encryption operation must use a unique nonce.

Create a strongly typed encryption envelope containing:

* version
* algorithm identifier
* nonce
* ciphertext
* authentication tag if represented separately
* optional associated-data version

Use associated authenticated data to bind ciphertext to relevant immutable context where appropriate.

Any modified ciphertext must fail authentication.

Never silently return partially decrypted data.

# 7. KEY ROTATION

Design the key hierarchy so that changing the master password does NOT require re-encrypting the entire vault.

Flow:

old master password
-> old KEK
-> decrypt VEK

new master password
-> new Argon2id
-> new KEK
-> encrypt VEK

The vault itself remains encrypted under the same random VEK unless a deliberate vault-key rotation is performed.

Implement versioned key envelopes.

## One architectural decision I'd emphasize

There are really **three separate secrets** in this system:

```text
                 ┌─────────────────────┐
                 │ Server Login Secret  │
                 │                     │
                 │ Authenticates user  │
                 └──────────┬──────────┘
                            │
                            │
                     SERVER SIDE
────────────────────────────┼────────────────────────
                            │
                      CLIENT SIDE
                            │
                 ┌──────────▼──────────┐
                 │   Master Password   │
                 │                     │
                 │ Unlocks vault keys   │
                 └──────────┬──────────┘
                            │
                         Argon2id
                            │
                 ┌──────────▼──────────┐
                 │       KEK           │
                 │                     │
                 │ Wraps vault key     │
                 └──────────┬──────────┘
                            │
                 ┌──────────▼──────────┐
                 │       VEK           │
                 │                     │
                 │ Encrypts vault      │
                 └──────────┬──────────┘
                            │
                       AES-256-GCM
                            │
                 ┌──────────▼──────────┐
                 │   Encrypted Vault   │
                 └─────────────────────┘
```

**That separation is the heart of the project.**

And one more important point: don't just build the crypto yourself and call it production-ready. A password manager is exactly the sort of application where an independent security review is worth doing before trusting it with real credentials.
